# FMOD 구조 개편 — 타임라인은 시계, 음정 레이어는 예약 원샷

작성 2026-11-24 · 상태: 승인 대기

## 1. 왜 하나

지금 음악은 이벤트 하나(`ChordPulseGame`, `Metadata/Event/{3d468f15…}.xml`) 위에 **모든 조합의 노트를 미리 깔고 파라미터 조건으로 끄는** 방식이다. 32마디(4개 템포 구간 × 8마디) 타임라인의 매 박에 "스타일 × 변형 × 콤보 × 긴장도 × 색 × 보이싱" 노트가 복사돼 있어서, 축 하나를 늘리면 노트가 곱으로 늘어난다.

- 겪은 문제: 노트 22,616개일 때 Studio 업데이트 CPU 90~150%(끊김, "Loading delay exceeded"), 저장 수 분, `fmodstudiocl` 저장 후 크래시로 뱅크 빌드 누락. 스타일별 처치 화음 1만 개를 빼서 지금은 노트 12,248개·XML 16MB·CPU 약 11%.
- 처치 화음은 홀짝 박 파라미터 + 0.4박 선행 무장 + 1.45박 길이 제한이라는 우회로 위에 있다(AdaptiveAudioPlan 10-3).
- **목표는 스타일·악기 같은 축을 계속 늘릴 수 있는 구조**다. 축을 하나 더할 때 비용이 곱이 아니라 합으로 늘어야 한다.

## 2. 목표 / 비목표 / 실패 기준

**목표**
- 새 스타일·악기·변형 추가 = 패턴 데이터 + 악기 이벤트 추가. 기존 이벤트를 고치지 않는다.
- 음악 이벤트 타임라인의 노트 수를 축 수와 무관하게 유지 (목표 1,000개 이하).
- 박 정확도는 지금 수준 유지 (아래 5-2 기준).
- 처치 화음을 스타일별 음색으로 되살리고, 홀짝 파라미터·1.45박 제한을 없앤다.

**비목표**
- 웹(HTML5) 빌드 개선. 웹은 데모 수준이며 현재 구조·뱅크로 고정한다.
- 연출(시각) 성능 최적화. 별도 작업.
- 템포 구간·구간 점프·피버 정렬 규칙 변경. 그대로 쓴다.

**실패 기준 (작동해도 실패)**
- 예약 원샷이 박에서 귀에 들릴 만큼 흔들리거나 늦다.
- 데스크톱 Studio CPU가 지금(약 11%)보다 의미 있게 높아진다.
- 같은 게임 상태에서 소리가 지금보다 나빠진다 (레벨·덕킹·필터가 원샷에 안 걸림 등).

## 3. 접근 (검토한 것)

| | 내용 | 장점 | 단점 | 결과 |
|---|---|---|---|---|
| A | 레이어를 스타일×BPM별 오디오 루프로 렌더 | Unity 변경 적음 | 뱅크 용량이 축 수에 비례, 노트 수정마다 재렌더 | 탈락 |
| **B** | **음정 레이어를 Unity가 박에 맞춰 원샷 예약 재생** | 축 추가 = 데이터 추가, 뱅크는 샘플만 | 예약 정확도·인스턴스 관리 필요 | **선택** |
| C | 이벤트만 레이어별로 쪼갬 | 저장 빨라짐 | 노트 곱셈 그대로 | 탈락 |

B 안에서 시계 선택: **FMOD 타임라인을 시계로 유지** (사용자 결정). Unity 시퀀서로 시계를 옮기는 안은 `MusicConductor`·구간 점프·피버 타이밍을 다시 써야 해서 탈락.

웹은 데모 수준이라 B의 웹 비용(메인 스레드 FMOD)은 고려하지 않는다 (사용자 결정).

## 4. 구조

```
[FMOD 음악 이벤트 = 시계]                       [Unity]
 템포 마커 · 구간 전환 마커 · 박 콜백  ───────▶  MusicConductor (박 → DSP 시각)
 코어 드럼(킥·스네어·클로즈드 햇)                     │
                                                       ▼
                                              PatternScheduler
   패턴 데이터 (Python 생성 → C#) ───────────▶  현재/다음 프레이즈 상태
   (레이어 × 스타일 × 변형 …, 4마디 단위)        (스타일·변형·콤보·긴장도·피버·특색 루프)
                                                       │ 0.5~1박 앞서 예약
                                                       ▼
[FMOD 악기 이벤트들]  event:/Inst/<악기>  ◀── Note·Velocity 파라미터 + 예약 시작
   └ 출력: 전역 믹서 버스 (Music Bed / Harmony / Kill Chords / Feature)
```

### 4-1. 타임라인에 남는 것
- 템포 마커, 구간 전환 마커(`NextSection`), 피버 정렬 마커 — 지금 그대로.
- 스타일과 무관한 코어 드럼: `Kick - beats 1 and 3`, `Snare - beats 2 and 4`, 클로즈드 햇. 박을 귀로 고정하는 기준.
- 그 외 모든 레이어(스타일 드럼 포함)는 예약 원샷으로 옮긴다. 스타일 드럼도 스타일 축으로 곱해지기 때문이다.

### 4-2. 악기 이벤트 (`event:/Inst/<악기>`)
- 악기(샘플 세트) 하나당 이벤트 하나. 파라미터 `Note`(MIDI), `Velocity`(0~1).
- 이벤트 안: `Note` 파라미터 시트에 샘플마다 건반 범위를 맡기고, 범위 안에서 피치를 반음 단위로 자동화 (지금 생성기의 "가장 가까운 샘플 + 피치" 규칙을 그대로 옮김). 레벨 보정값(생성기 표의 RMS·어택 오프셋)도 여기 넣는다.
- 드럼 키트는 `Note` = 타악기 번호로 같은 방식.
- 출력은 이벤트 내부 그룹이 아니라 **전역 믹서 버스**. 버스 구조는 지금 이벤트 내부 구조를 그대로 옮긴다: `Music Bed`(Kick/Snare/…/Bass) · `Harmony`(사이드체인 덕킹 대상) · `Kill Chords`(사이드체인 소스·컴프·리미터) · `Feature`.
- 이벤트 설정: Max Instances + 스틸링(오래된 것부터), 악기별 상한은 생성기가 지정.

### 4-3. 파라미터 이전
지금 음악 이벤트 안에서 그룹 볼륨·필터를 자동화하는 파라미터는 버스에 걸려야 원샷에도 적용된다.
- `MusicMix`, `KillChordMix` → 버스 볼륨 (Unity에서 `Bus.setVolume`) 또는 전역 파라미터.
- `Tension`(Music Bed 로우패스), `Hurt`(덕킹), `Danger` → **전역 파라미터**로 바꾸고 버스 이펙트에 자동화.
- `BedStyle`, `Variation`, `Combo`, `FeatureLoop`, `RedKills` 등 "무엇을 연주할지" 파라미터 → FMOD에서 사라지고 `PatternScheduler` 입력이 된다. 결정 시점(프레이즈 경계 직전, 마디 경계 등)은 지금 `SoundManager` 규칙 그대로.

### 4-4. 패턴 데이터
- 원천은 지금처럼 `FMOD/Tools/*.py`. 생성기가 FMOD에 노트를 까는 대신 **패턴 표를 C#으로 생성**한다 (`BedNotes.g.cs`, `FeatureLoopNotes.g.cs`와 같은 방식을 확장).
- 패턴 = 4마디 프레이즈 안의 `(박, MIDI, 길이, 세기, 악기)` 목록 + 적용 조건(레이어, 스타일, 변형, 콤보 단계, 긴장도 구간, 피버 단계). 코드 진행이 모든 구간에서 C–Am–F–G라 4마디 하나로 32마디를 대신한다.
- 같은 데이터를 연출(`MusicReactiveVisuals`, 특색 루프 연출)도 읽는다. 예약된 노트를 그대로 연출 이벤트로 내보내면 소리와 연출이 같은 원천을 공유한다.
- 악기 이벤트 JS도 같은 생성기가 만든다 (악기당 샘플 수십 개 수준이라 스크립트가 작다 → 크래시 위험 낮음).

### 4-5. PatternScheduler (Unity)
- 매 프레임, 지금부터 룩어헤드(초기값 1박, 실측으로 조정) 안에 들어오는 노트를 골라 아직 예약하지 않은 것만 예약.
- 박 → DSP 시각 변환은 `MusicConductor` 확장 (5-1 스파이크 결과에 따라 방식 결정).
- 구간 점프: 다음 구간은 `SectionSelector`가 한 프레이즈 앞서 알고 있으므로, 경계 너머 노트는 다음 구간 BPM으로 계산. 점프가 예상과 다르게 일어나면(피버 보류 등) 경계 너머 예약분을 취소하고 다시 예약.
- 정지·재시작·씬 종료 시 예약 인스턴스 전부 정리.
- 처치 화음: `QueueKillChord`가 목표 박과 색·보이싱을 받으면, 그 박의 코드(마디 → C/Am/F/G)와 현재 스타일 악기로 음을 골라 예약. 홀짝 파라미터·무장/해제 로직 삭제.
- **처치 화음 반응 속도는 지금과 같게**: 배경 레이어의 1박 룩어헤드를 쓰지 않는다. 지금처럼 다음 박이 0.4박 이상 남았으면 다음 박, 아니면 그 다음 박에 예약한다 (`ChordLeadBeats` 규칙 유지). 따라서 예약 방식은 **0.4박 미만의 선행 시간**으로도 정확해야 한다 (5-1에서 함께 검증).
- 처치 화음 스타일별 악기 표는 실제로 구현됐던 `kill_voices.py` / AdaptiveAudioPlan 9-7의 표를 기준으로 한다 (9-2 초안 표가 아님).
- **확장음도 복원** (사용자 결정): 콤보 2 이상 → 코드 7음, 콤보 3 → 포먼트 벨 옥타브, 긴장도 0.65 이상 → 낮은 루트음 펀치. 따라서 처치 화음 예약 시 스케줄러는 현재 `Combo`·`Tension` 값을 함께 읽는다. 피버 중에는 지금처럼 스타일 0·콤보 0·긴장도 0 (원래 처치 화음).

## 5. 검증

### 5-0. 측정 기준 만들기 (스파이크 전)
원샷은 Unity가 예약하므로 FMOD 이벤트만 렌더하는 지금 검증 방식으로는 들을 수 없다. Unity 플레이 중 FMOD 출력을 WAV로 남기는 캡처(Core `OUTPUTTYPE.WAVWRITER_NRT` 또는 `WAVWRITER`, 고정 시드·스크립트된 처치 입력)를 먼저 만들고, **지금 구조로 기준 녹음을 다시 뜬다.** 이후 모든 레벨·타이밍 비교는 같은 캡처끼리 한다.
- 스타일별 처치 화음은 레벨 검증 전에 제거돼 "이전" 녹음이 없다 → 목표 레벨은 신스팝 처치 화음 기준(AdaptiveAudioPlan 9-5: 3색 × 3음 매 박 RMS 약 -21.7 dBFS)에 ±1 dB.

### 5-1. 첫 단계는 스파이크: 예약 정확도
`EVENT_PROPERTY.SCHEDULE_DELAY`가 "지정한 DSP 시각에 샘플 단위로 시작"을 보장하는지 문서만으로 확실하지 않다. 처치 화음 하나만 원샷으로 만들어 측정한다.
- 후보 ① Studio 이벤트 + `SCHEDULE_DELAY`/`SCHEDULE_LOOKAHEAD`
- 후보 ② 이벤트 시작 후 채널 그룹에 Core `setDelay(dspStart)`
- 박 DSP 시각을 얻는 방법도 함께 측정: 음악 이벤트 채널 그룹 `getDSPClock` + 타임라인 위치, 또는 박 콜백 시점 기록.
- 오프라인 렌더(지금 검증 방식)로 타임라인 킥 어택 대비 원샷 어택 오차를 잰다.

### 5-2. 합격 기준
- 박 대비 어택 오차: 평균 ≤ 2 ms, 최대 ≤ 5 ms (구간 점프 직후 포함).
- Studio CPU(`getCPUUsage`): 모든 레이어 이전 후 지금(약 11%) 이하, 동시 처치 많은 장면 포함.
- 레벨: 이전 전후 렌더 RMS 차이 레이어별 ±1 dB, 덕킹·Tension 필터·Hurt가 원샷 레이어에도 걸림.
- FMOD 프로젝트 저장이 수 초 안에 끝남. 음악 이벤트 노트 ≤ 1,000.
- 확장성 확인: 새 스타일 하나를 데이터 + 악기 이벤트만으로 추가해 기존 이벤트 파일이 바뀌지 않음.

## 6. 진행 순서

0. **캡처 기준 만들기** (5-0): Unity 구동 WAV 캡처 + 현재 구조 기준 녹음. 웹 데모 태그도 이때 남긴다 (HTML5 뱅크도 같은 FMOD 프로젝트에서 빌드되므로, 트랙을 지우기 전에).
1. **스파이크**: 처치 화음 1색 원샷 + 예약 정확도 측정 (5-1, 0.4박 미만 선행 포함). 기준 미달이면 여기서 멈추고 다시 논의.
2. **처치 화음 전체 이전**: 스타일별 음색 복원, 홀짝 로직 삭제, `Kill Chords` 버스로 믹싱 이전.
3. **믹서·전역 파라미터 이전** (4-3): 버스 구조, Tension/Hurt/Danger 전역화.
4. **배경 음정 레이어 이전**: 베이스·플럭 → 스타일 화성(라틴 마림바, 펑크 키/기타, 드리미) → 콤보·긴장도 레이어.
5. **스타일 드럼 이전**: 펑크 드럼, 라틴 셰이커/퍼커션, 드리미 퍼커션, 하이햇 변형.
6. **특색 루프 이전**: `FeatureLoopNotes` 데이터를 원천으로.
7. **피버 레이어 이전**: 빌드업 롤·라이저, 아웃트로, 피버 리드·셰이커·베이스 5도.
8. 음악 이벤트 정리: 옮긴 트랙 삭제, 노트 수·CPU·저장 시간 확인, AdaptiveAudioPlan 문서 갱신.

각 단계 끝에 렌더 비교로 이전 전과 같은 소리인지 확인한다. 단계 2 이후로는 옛 트랙을 지우기 전까지 파라미터로 옛/새 경로를 바꿔 들어볼 수 있게 둔다.

## 7. 내가 정한 것 (확인 필요)

- 웹 데모는 지금 커밋을 태그(예: `web-demo`)로 남겨 그 시점에서 빌드한다. 새 구조는 데스크톱 전용.
- 코어 드럼(킥·스네어·클로즈드 햇)은 타임라인에 남긴다.
- 패턴 데이터 형식은 ScriptableObject가 아니라 지금처럼 생성된 C# 표 (`*.g.cs`). 기존 생성기 흐름과 맞추기 위함.
- 룩어헤드 초기값 1박.

## 8. 빌더에게 남기는 것

- 예약 방식(5-1 후보 ①/②)과 박 DSP 시각 계산법 — 스파이크 결과로 결정.
- 악기별 Max Instances 값, 스틸링 규칙 세부.
- 패턴 C# 표의 정확한 모양, 연출로 노트 이벤트를 내보내는 API 모양.
- 생성기 파일 구성 (기존 `bed_*.py`를 고칠지, 새 `patterns.py`로 모을지).
