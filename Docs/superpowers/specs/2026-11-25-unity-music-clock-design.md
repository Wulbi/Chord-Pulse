# 음악 시계를 Unity로 — 타임라인 점프 제거

작성 2026-11-25 · 상태: 승인 대기
앞선 문서: `2026-11-24-fmod-scheduled-layers-design.md`(이하 "1차 스펙"), 계획 `../plans/2026-11-25-fmod-scheduled-layers-stages-3-8.md`(이하 "3~8단계 계획")

## 1. 왜 하나

프레이즈 경계에서 소리와 박자가 순간적으로 끊긴다. 프레임 문제가 아니다(캡처 테이크에서 100 ms 넘는 프레임 0회).

측정(`Docs/Captures/baseline_seed7_jumpcheck.wav`, 2026-11-25, Editor, seed 7, 128박):

| 경계(박) | 템포 | 타임라인 점프 | 착지 박 콜백 지연 | 첫 반 박 음량 (이전 프레이즈 같은 자리) |
|---:|---|---|---:|---|
| 16 | 108→108 | 없음 | +1 ms | -31.5 dB (-31.2) |
| 32 | 108→116 | 없음(이어지는 자리) | -2 ms | -31.1 dB (-31.2) |
| 112 | 116→116 | 없음 | +6 ms | -32.7 dB (-32.8) |
| 64 | 108→108 | 없음 | +95 ms | -33.3 dB (-31.2) |
| 48 | 116→108 | 있음 | +350 ms | -46.1 dB (-30.9) |
| 80 | 108→108 | 있음(같은 구간 처음으로) | +321 ms | 무음 (-33.3) |
| 96 | 108→116 | 있음 | +823 ms | -39.3 dB (-33.3) |

- 점프가 있는 경계에서만 FMOD Studio가 0.2~0.8초 멈춘다. 템포 변화 자체는 원인이 아니다(32박). 어제 테이크 2개와 seed 33 테이크(점프 4회를 타임라인 위치 로그로 확인, 4회 모두 +217~236 ms)도 같다. seed 7의 "점프 있음/없음"은 구간 배치(구간당 8마디)에서 추론한 것이다.
- 연출과 게임의 박(`SoundManager.BeatPosition`)은 타임라인 박 콜백에 묶여 있어, 착지 콜백이 늦는 동안 직전 박 + 0.999에서 멈췄다가 뛴다(`MusicConductor.MaxExtrapolationBeats`). 화면이 굳어 보이는 이유다.
- 이 정지 중에 만든 원샷 인스턴스는 버려진다(1차의 R12). 3~8단계가 레이어를 원샷으로 옮길수록 이 피해가 커진다.
- 64박의 +95 ms는 점프가 아닌 자리인데 세 테이크 모두에서 나온다. 원인 미확인.

1차 스펙은 "FMOD 타임라인을 시계로 유지"를 택했다. 이 문서는 그 결정을 뒤집는다(사용자 결정, 2026-11-25). 3~8단계가 끝나면 템포 구간끼리 다른 것은 템포뿐이라, 타임라인과 점프는 템포를 바꾸는 용도로만 남는다. 그 마지막 조각을 떼어낸다.

## 2. 목표 / 비목표 / 실패 기준

**목표**
- 프레이즈 경계(템포 전환 포함)에서 소리가 비지 않고 박이 멈추지 않는다.
- 박의 정의가 하나다: FMOD 마스터 채널 그룹 DSP 클럭의 샘플 번호. 소리(예약 원샷)와 연출·게임이 같은 시계를 읽는다.
- 새 템포 구간·스타일을 추가해도 FMOD 이벤트를 고치지 않는다(1차 스펙 목표의 연장).

**비목표**
- 웹(HTML5) 빌드. `web-demo` 태그로 고정.
- 연출 코드(`Assets/Scripts/Visual/*`) 수정. 연출은 지금처럼 `SoundManager`의 공개 값만 읽는다.
- 템포 구간 선택 규칙, 피버 정렬 규칙, 편성 결정 규칙 변경.
- 일시정지 후 "같은 음악 위치에서 정확히 이어 재생". 게임에 일시정지 기능이 아직 없다. 요구는 4-5의 "깨지지 않는다"까지다.
- FMOD Studio 안에서 게임 음악을 통으로 미리 듣기(사용자 답 없음 → 내가 정함, 7장).

**실패 기준 (작동해도 실패)**
- 박 대비 어택 오차가 1차 기준(평균 ≤ 2 ms, 최대 ≤ 5 ms)을 넘는다.
- 일반적인 프레임 흔들림(≤ 100 ms)에서 드럼이 빠진다.
- 오래 틀어 두면 소리와 화면 박이 벌어진다.
- Core DSP CPU가 3~8단계 계획의 예산(baseline ≤ 6%, heavy ≤ 12%)을 넘는다.

## 4. 구조

```
[Unity]
 SectionSelector ──(다음 프레이즈 템포, 한 프레이즈 앞서)──▶ 음악 시계
                                                              │  박 ↔ DSP 샘플 (구간별 템포)
        ┌─────────────────────────────────────────────────────┤
        ▼                                                     ▼
 PatternScheduler / KillChordPlanner                 연출·게임용 박
 (코어 드럼 포함 모든 레이어)                         (프레임 사이 보간, 출력 지연 보정)
        │ OneShotScheduler
        ▼
[FMOD] event:/Inst/* 원샷 → 전역 믹서 버스     ※ 음악 이벤트·타임라인·박 콜백 없음
```

### 4-1. 음악 시계
- 박 0 = 음악 시작 시 정한 DSP 샘플(`지금 + 시작 여유`). 이후 박 ↔ 샘플은 순수 계산이다. FMOD 콜백을 기다리지 않는다.
- 템포는 프레이즈 단위로만 바뀐다. 프레이즈 경계의 샘플 번호를 **정수로 한 번 확정**하고, 그 프레이즈 안의 박은 그 정수에서 계산한다. 반올림 오차가 프레이즈를 넘어 쌓이지 않는다.
- 다음 프레이즈의 템포는 지금처럼 `SectionSelector`가 한 프레이즈 앞서 정한다. 피버가 뒤늦게 다음 구간을 붙잡으면(`HoldNext`) 경계 너머 템포가 바뀌고, 이미 넘긴 경계 너머 노트는 다시 예약한다(`RescheduleFrom`, 이미 있음).
- 템포의 원천은 `SectionSelector.Bpm` 하나다. FMOD 템포 마커와 맞추는 일이 없어진다.
- 순수 로직(FMOD·Unity API 없음)으로 두고 EditMode 테스트한다. 지금의 `BeatClock`을 고쳐 쓸지 새로 쓸지는 빌더가 정한다.
- `OneShotScheduler.ScheduleOffsetSamples`(-110)는 "타임라인 박보다 원샷이 늦는 만큼"의 보정이었다. 맞출 타임라인이 없어지므로 0이 된다.

### 4-2. 연출·게임용 박
- `SoundManager.BeatPosition` / `CurrentBeat` / `CurrentStep` / `CurrentBar` / `BeatSeconds` / `CurrentBpm` 등 공개 값의 뜻은 그대로("지금 들리는 박"), 원천만 음악 시계로 바뀐다. 0.999 상한은 없앤다.
- 메인 스레드에서 읽는 DSP 클럭은 믹서 블록(1024샘플, 약 21 ms)마다만 바뀐다. 프레임 사이를 보간해 매끄럽게 하고, 뒤로 가지 않게 한다. 보간 방법은 빌더가 정한다(5장 기준).
- 출력 지연 보정 `visualLatencyMs`는 유지한다.
- `CurrentSection`(타임라인 마커 이름)은 쓰는 곳이 없다. 지운다.

### 4-3. 코어 드럼
- 킥·스네어·닫힌 햇도 패턴 데이터의 한 레이어가 된다. 3~8단계 계획 Task 12의 "코어 드럼은 타임라인에 남기고 `CoreKick`·`CoreBackbeat` 이벤트 파라미터로 게이트"를 **대체**한다: 킥은 "피버 빌드업이 아닐 때", 스네어·닫힌 햇은 "코어 백비트를 쓰는 스타일일 때"를 패턴 클립 조건으로 표현한다.
- 코어 드럼은 한 프레이즈 앞서 정해지는 것(스타일·피버)에만 달려 있으므로 **한 마디 앞까지** 미리 FMOD에 넘긴다. 일반적인 프레임 정지에도 드럼이 끊기지 않게 하기 위함이다. 피버가 뒤늦게 정해지면 다른 레이어처럼 취소하고 다시 예약한다.
- 나머지 레이어의 룩어헤드는 3~8단계 계획 그대로(1박). 처치 화음 규칙(0.4박)도 그대로.

### 4-4. 사라지는 것
- 런타임의 `event:/Music/ChordPulseGame` 인스턴스, `NextSection` 파라미터, 템포 마커·전환 마커, `MusicConductor`의 타임라인 콜백 경로.
- 편성 파라미터 리드(`RhythmLookahead` 0.25초)와 "Loading delay exceeded" 대응. 타임라인 노트를 게이트할 일이 없다. 단, `QueueFever`가 같은 0.25초를 "빌드업 마디까지 남아야 하는 최소 시간"으로도 쓴다. 이 문턱은 피버 정렬 규칙이므로 이름만 바꿔 남긴다.
- 점프 정지 우회로: 착지 직후 1박 앞서 넘김(R15, `PostBoundaryDispatchBeats`), 반 박 뒤 앵커 고정(R14). 최종 측정에서 필요 없음이 확인되면 지운다.
- 3~8단계 계획 Task 4의 `SectionBpm_MatchesFmodTempoMarkers` 테스트, `Spike ref` 타임라인 트랙(측정 기준이 5장으로 바뀜).
- FMOD 프로젝트의 음악 이벤트 자체는 마지막 단계에서 삭제한다. `event:/Music/ChordPulsePreview`(`FMODMusicPreview` 씬)는 별개라 건드리지 않는다.

### 4-5. 깨지면 안 되는 상황
- **긴 프레임 정지**(로딩, GC, 에디터 포커스 이탈): 시작 시각이 지난 노트는 버린다(1차의 "절대 늦게 울리지 않는다" 유지). 정지가 끝나면 음악은 **제 위치에서** 이어진다. 밀린 노트가 몰아서 울리거나 박이 어긋나면 안 된다.
- **일시정지·백그라운드**: 재개 후 밀린 노트가 몰아서 울리지 않고, 소리와 화면 박이 같은 시계를 유지한다. 그동안 음악 위치가 흘러가 있어도 된다.
- **출력 장치 변경 등으로 DSP 클럭이 뒤로 가거나 샘플레이트가 바뀜**: 멈추거나 예외 없이, 한 마디 안에 다음 마디 첫 박부터 다시 맞춰 이어진다.
- **정지·재시작·게임 오버**: 예약분과 울리는 소리가 남지 않는다(3~8단계 계획 Task 2·6의 규칙 그대로).

## 5. 검증

캡처 방식은 `Docs/Captures/README.md` 그대로. 박 로그(`.beats.csv`)는 콜백 시각 대신 음악 시계의 계산값(박 → 캡처 프레임)으로 쓴다.

- **경계 공백 없음**: seed 7(128박)과 seed 33(68박)의 모든 프레이즈 경계에서 첫 반 박 RMS가 이전 프레이즈 같은 자리 대비 ±1 dB(편성이 같은 경계끼리), 20 ms 넘는 무음 0곳. 1장 표의 64박(+95 ms 자리)도 포함해 다시 잰다.
- **어택 정확도**: 매 박에 예약한 시험 클릭(`SpikeClick`)의 어택이 계산된 샘플 위치 대비 평균 ≤ 2 ms, 최대 ≤ 5 ms. 템포가 바뀐 직후 4박을 따로 집계.
- **누적 오차 없음**(EditMode): 템포가 매 프레이즈 바뀌는 10분 분량에서, 마지막 프레이즈 경계의 샘플 번호가 독립 계산(프레이즈 길이의 정수 합)과 일치.
- **화면 박이 매끄러움**: 프레임 정지 0회 테이크에서 프레임마다 `BeatPosition` 증가량을 기록 → 뒤로 간 적 0회, 기대값(`dt × bpm / 60`)과의 차이 최대 0.05박 이하. 경계 포함.
- **프레임 정지 내성**: `CaptureScenario`에 강제 정지(메인 스레드 300 ms 대기, 프레이즈 중간과 경계 직전에 한 번씩) 옵션 → 코어 드럼 누락 0, 늦게 울린 노트 0, **일찍 울린 노트 0**, 정지 뒤 어택 정확도 기준 통과. 2초 정지에서는 누락은 허용, 늦은·이른 노트 0, 재개 뒤 정확도 통과. (이른 노트: 인스턴스를 시작한 뒤 시작 시각을 거는 사이에 프레임이 멈추면 예약 시각보다 먼저 울릴 수 있다. 한 마디 앞서 넘기는 코어 드럼에서 드러나기 쉬우므로 따로 센다.)
- **스탠드얼론**: 최종 측정에는 Windows 빌드의 baseline·heavy 테이크를 포함한다(3~8단계 계획 Task 15와 같음).
- **CPU**: 3~8단계 계획의 예산 그대로(Studio update 평균 ≤ 11%, Core dsp baseline ≤ 6% / heavy ≤ 12%), 코어 드럼 원샷 포함.
- **레벨**: 코어 드럼 이전 전후 Music Bed 솔로 RMS ±1 dB(3~8단계 계획의 레이어 이전 기준과 같음).
- 수동 Play: 템포 전환, 피버 진입·종료, 숨 고르기, 게임 오버 → 재시작에서 끊김·잔류음 없음.

## 6. 진행 순서

1. **연출·게임 박을 DSP 클럭 기반으로** (지금, 3~8단계 계획과 독립). 타임라인은 그대로 두고, `BeatPosition` 계열이 0.999 상한 없이 `BeatClock`(1차에서 이미 점프 착지를 넘어 외삽함)을 읽게 한다. 화면 굳음이 여기서 풀린다. **소리 공백은 남는다.** 고치는 파일은 `SoundManager`·`MusicConductor`와 테스트뿐이다. 바꾸는 것은 공개 값뿐이다: 프레이즈 진행(`UpdatePhrase`)과 `NextSection`·편성 파라미터를 쓰는 시점은 3단계까지 타임라인 콜백 기준 그대로 둔다(Studio가 착지에서 멈춰 있는 동안 쓰는 시점을 바꾸는 것은 검증되지 않은 위험). 이 단계에서 64박의 +95 ms도 진단한다(그 경계에서 바뀌는 파라미터를 하나씩 고정해 녹음) — 점프가 아니라서 시계 전환 뒤에도 남을 수 있다.
2. **3~8단계 계획 실행.** 바뀌는 점:
   - Task 12: 코어 드럼도 패턴으로 옮긴다(4-3). `core_drums.py`·`CoreKick`·`CoreBackbeat`는 만들지 않는다. 이 Task 끝에서 CPU 예산을 넘으면 계획에 적힌 대로 멈추고 보고.
   - Task 4: 템포 마커 대조 테스트는 3단계에서 지워질 임시 안전장치로만 둔다.
   - 점프 정지 체크포인트(Task 11 Step 4)는 "별도 계획을 쓸지 보고"가 아니라 측정 기록만 한다. 답은 이 문서다.
3. **시계 전환** (3~8단계 계획 Task 14 뒤, Task 15를 대체·확장). 타임라인에 들리는 노트가 하나도 없을 때만 가능하다. 음악 시계를 스스로 가게 하고(4-1), 음악 이벤트 시작·`NextSection`·콜백 경로를 지우고(4-4), 5장 전체를 측정한 뒤 FMOD 프로젝트에서 음악 이벤트를 삭제한다. 옛/새 경로 A/B(`LegacyLayers`)는 여기서 끝난다.

1단계와 3단계 사이, 즉 3~8단계를 진행하는 동안 소리 공백은 남고, 원샷으로 옮긴 레이어는 착지 직후 노트가 빠질 수 있다(R15가 대부분 막음). 그 기간을 줄이려고 타임라인 쪽을 임시로 손보지는 않는다.

## 7. 내가 정한 것 (확인 필요)

- FMOD Studio 안 게임 음악 미리듣기는 포기하고 음악 이벤트를 삭제한다. 들어 보는 수단은 Unity 캡처 씬이다.
- 코어 드럼 룩어헤드는 한 마디, 나머지는 1박. 실측으로 조정 가능.
- 일시정지 후 정확한 위치 재개는 범위 밖(4-5의 "깨지지 않는다"까지).
- 3~8단계를 진행하는 동안 소리 공백을 임시로 줄이는 작업은 하지 않는다.
- 시계 전환을 3~8단계 계획 맨 끝(Task 14 뒤)에 둔다.
- 1단계는 공개 박 값만 바꾸고 내부 타이밍은 건드리지 않는다. 64박 지연 진단을 1단계에 넣는다.
- 강제 정지 테스트에서 "일찍 울린 노트"도 센다. 최종 측정에 스탠드얼론 테이크를 넣는다.
- 이 문서는 커밋하지 않았다(요청 시 커밋).
