# Chord Pulse — 특색 루프 연출 데이터 구조 설계

> [AdaptiveAudioPlan.md 7-4절](AdaptiveAudioPlan.md)의 "루프 = 연출 세트"를 실제 코드 구조로 옮기기 위한 설계.
> 루프별로 무엇을 보여줄지(손님 12종 + 배경 적응형 축)는 [MusicVisualsPlan.md](MusicVisualsPlan.md)에 있다. 이 문서는 그 연출을 담을 코드 구조다.
> 목표: `FeatureLoopVisuals.cs`에 하드코딩된 혜성/새 연출을 **데이터(`FeatureLoopData`) + 교체 가능한 연출기(Emitter)** 구조로 일반화해서, 루프나 악기를 추가할 때 C# 분기를 늘리지 않고 에셋과 스타일 클래스 하나만 추가하면 되게 만든다.

---

## 0. 현재 상태 (2026-11-24 기준)

### 데이터 흐름

```
FMOD/Tools/feature_loops.py ──┬─► FMOD 이벤트 (Feature 트랙, FeatureLoop 파라미터)
                              └─► Assets/Scripts/Audio/FeatureLoopNotes.g.cs (음표 온셋)

FeatureSelector.Loops (손으로 쓴 표) ─► SoundManager.CurrentFeature / UpcomingFeature
                                               │
FeatureLoopVisuals.SpawnFromMusic() ◄──────────┘  박 위치로 음표를 읽어서 Launch(note)
```

### 하드코딩된 부분

| 위치 | 내용 | 문제 |
|---|---|---|
| `Launch()` | `note.Whistle`이면 새, 아니면 혜성 | 악기가 2종일 때만 맞는 구조. 마림바·퍼커션·신스·기타가 전부 혜성으로 나감 |
| 상수 | `CometSeconds`, `BirdSeconds`, `CometColor`, `BirdColor`, 크기, 궤적 | 튜닝하려면 코드를 고쳐야 함 |
| `LowMidi`/`HighMidi` = 62~98 | 음 높이를 화면 높이로 바꾸는 범위가 하나뿐 | 기타(MIDI 43)는 화면 맨 아래에 붙고, 퍼커션(전부 72)은 한 줄로만 나옴 |
| `Announce()` | 트럼펫이 있으면 혜성색, 아니면 새색으로 반짝임 | 루프별 예고 연출을 바꿀 수 없음 |
| `Flyer` 클래스 | 혜성과 새가 한 클래스에 `IsBird` 플래그로 섞여 있음 | 새 연출 형태(파동, 링 회전 등)를 넣을 자리가 없음 |

### 데이터 불일치 (설계 전에 먼저 해결해야 함)

- `feature_loops.py`와 `FeatureLoopNotes.g.cs`에는 **12개 루프, 6개 악기 플래그**가 있다
  (`trumpet 1, whistle 2, mallets 4, perc 8, synth 16, guitar 32`).
- `FeatureSelector.Loops`는 **6개 루프만**, `Instrument` enum은 **Trumpet/Whistle만** 정의돼 있다.
  → 7~12번 루프(Latin Groove, Marimba Run, Glock Sparkle, Synth Hook, Power Chord Hits, Mallet Hook)는 음표 데이터는 있지만 선택되지 않는다. 생성 코드에는 `(FeatureSelector.Instrument)8`처럼 enum에 없는 값이 들어가 있다.
- 루프 표가 Python과 C# 두 곳에 손으로 따로 적혀 있어서 생긴 문제다. 1단계에서 이걸 하나로 합친다.

## 1. 설계 원칙

1. **오디오 사실은 Python에만 둔다.** id, 이름, 시작 마디, 길이, 악기 구성, 음표는 `feature_loops.py`가 정하고 C#으로 생성한다. Unity에서 손으로 다시 쓰지 않는다.
2. **연출과 선택 튜닝은 Unity 에셋에 둔다.** 색, 궤적, 분위기 태그, 가중치처럼 귀나 눈으로 맞추는 값은 ScriptableObject에서 고치고, Play 모드에서 바로 확인한다.
3. **연출은 악기(목소리) 단위, 덮어쓰기는 루프 단위로 한다.** 기본적으로 "트럼펫 음 = 혜성"처럼 악기마다 스타일이 하나 있다. 특정 루프만 다르게 보여야 할 때(예: Call and Response에서 좌우 번갈아 가기) 루프 데이터에서 덮어쓴다. 6-2절의 "역할 기반 공통 연출 + 시그니처 override" 구조와 같다.
4. **박 계산은 한 곳에서만 한다.** 음표를 언제 쏠지는 디렉터(`FeatureLoopVisuals`)가 정하고, 연출기는 "지금 이 음을 그려라"만 받는다. 연출기는 FMOD나 `SoundManager`를 모른다.
5. **에셋이 없어도 돌아가야 한다.** 이 프로젝트는 씬 와이어링 없이 코드로 오브젝트를 만들기 때문에, 라이브러리 에셋이 없으면 지금과 같은 기본값(혜성/새)으로 동작한다.

## 2. 구조 개요

```
[생성]  FeatureLoopCatalog.g.cs     ← feature_loops.py
          ├─ enum FeatureInstrument (Flags: Trumpet, Whistle, Mallets, Perc, Synth, Guitar)
          ├─ LoopInfo[] Loops        (id, name, startBar, bars, instruments)
          └─ Note[][] NotesById      (beat, instrument, midi, voices)

[에셋]  FeatureLoopLibrary (ScriptableObject, Resources/)
          ├─ VoiceDefault[]          악기 → 기본 FeatureVisualStyle
          └─ FeatureLoopData[]       루프별 연출·선택 튜닝 (id로 카탈로그와 연결)

        FeatureVisualStyle (abstract ScriptableObject)
          ├─ CometStyle      (트럼펫)
          ├─ BirdStyle       (휘파람)
          ├─ RippleStyle     (신스)        ← 신규
          ├─ RimOrbitStyle   (퍼커션)      ← 신규
          ├─ ChimeStyle      (말렛류)      ← 신규
          └─ ShockStyle      (기타)        ← 신규

[런타임] FeatureLoopVisuals (디렉터, MonoBehaviour)
          ├─ 박 추적·음표 스케줄링 (지금 SpawnFromMusic 그대로)
          ├─ 예고(Announce) 타이밍
          └─ IFeatureEmitter[]  스타일마다 하나씩, 자기 풀을 직접 관리
```

## 3. 데이터 정의

### 3-1. 생성 카탈로그 `FeatureLoopCatalog.g.cs`

`feature_loops.py`의 `write_cs()`를 확장해서 지금의 `FeatureLoopNotes.g.cs`를 대체한다.

```csharp
// Generated by FMOD/Tools/feature_loops.py
[System.Flags]
public enum FeatureInstrument { None = 0, Trumpet = 1, Whistle = 2, Mallets = 4, Perc = 8, Synth = 16, Guitar = 32 }

public static class FeatureLoopCatalog
{
    public readonly struct LoopInfo
    {
        public readonly int Id; public readonly string Name;
        public readonly int StartBar; public readonly int Bars;
        public readonly FeatureInstrument Instruments;   // 음표에서 자동으로 OR
    }
    public readonly struct Note
    {
        public readonly float Beat;          // 프레이즈 안 박 (0..16)
        public readonly FeatureInstrument Instrument;
        public readonly int Midi;
        public readonly int Voices;
        public readonly int Index;           // 루프 안에서 이 악기의 몇 번째 음인지 (좌우 교대·색 순환용)
    }

    public static readonly LoopInfo[] Loops = { /* 1..12 */ };
    public static readonly Note[][] NotesById = { null, /* 1..12 */ };
}
```

- `Whistle` bool은 없앤다. `Instrument`로 판단한다.
- `Instruments`는 Python이 음표에서 계산하므로 표와 음표가 어긋날 수 없다.
- `FeatureSelector.Loop`은 `LoopInfo`를 감싸거나 그대로 쓴다. 손으로 쓴 `Loops` 배열은 지운다.

### 3-2. 루프 데이터 `FeatureLoopData`

7-4절에서 계획한 구조에서 오디오 사실(라벨 값, 길이, 온셋)은 카탈로그로 옮기고, 튜닝 값만 남긴다.

```csharp
[CreateAssetMenu(menuName = "Chord Pulse/Feature Loop Data")]
public sealed class FeatureLoopData : ScriptableObject
{
    public int loopId;                         // FeatureLoopCatalog.Loops의 Id
    public FeatureMood mood;                   // Calm / Hype / Fever  (7-3 선택 규칙)
    [Range(0, 3)] public float baseWeight = 1; // 선택 가중치. 0이면 비활성
    public bool allowInBreath;                 // 숨 돌리기 프레이즈 허용 여부

    public Color accent = Color.white;         // 예고 반짝임과 공통 연출 틴트에 쓰는 대표 색
    public AnnounceStyle announce;             // EdgeTwinkle / RimPulse / None

    public VoiceOverride[] voices;             // 비어 있으면 라이브러리 기본값 사용
}
// 경계 링과 배경은 손님 루프가 아니라 배경 루프 상태가 정한다 (MusicVisualsPlan.md 2-0).
// 손님 데이터에는 링·배경 필드를 두지 않는다.

[System.Serializable]
public struct VoiceOverride
{
    public FeatureInstrument instrument;
    public FeatureVisualStyle style;           // null이면 기본 스타일 유지
    public SideMode side;                      // Alternate / Left / Right / ByPitch / CallResponse
    public float sizeScale;                    // 1 = 기본
}
```

### 3-3. 라이브러리 `FeatureLoopLibrary`

```csharp
public sealed class FeatureLoopLibrary : ScriptableObject
{
    public VoiceDefault[] voiceDefaults;   // instrument → FeatureVisualStyle
    public FeatureLoopData[] loops;
    public int maxActiveVisuals = 48;      // 전체 예산 (아래 5절)

    public FeatureLoopData Find(int loopId);
    public FeatureVisualStyle StyleFor(FeatureLoopData loop, FeatureInstrument instrument);
}
```

- 위치: `Assets/Resources/FeatureLoopLibrary.asset`. 디렉터가 `Resources.Load`로 읽는다.
- 없으면 `FeatureLoopLibrary.CreateDefault()`가 지금 코드와 같은 값의 혜성/새 스타일을 메모리에 만든다(원칙 5).

### 3-4. 연출 스타일 `FeatureVisualStyle`

스타일 에셋은 "값 + 연출기 생성기"다. 실제로 오브젝트를 들고 움직이는 건 런타임 연출기다.

```csharp
public abstract class FeatureVisualStyle : ScriptableObject
{
    public Color color = Color.white;
    public Vector2Int midiRange = new Vector2Int(62, 98);   // 음 높이 → 화면 높이 매핑 범위
    public float seconds = 1f;
    public float size = 0.25f;
    public abstract IFeatureEmitter CreateEmitter(FeatureVisualContext ctx);
}

public sealed class CometStyle : FeatureVisualStyle
{
    public float arc = 0.5f, trailTime = 0.35f, voiceSpread = 0.45f, chordSizeScale = 1.33f;
    public override IFeatureEmitter CreateEmitter(FeatureVisualContext ctx) => new CometEmitter(this, ctx);
}
```

`midiRange`를 스타일마다 두면 기기 음역 문제(기타 43, 퍼커션 72 고정)가 풀린다.
퍼커션처럼 음 높이가 의미 없는 악기는 스타일 안에서 `Voices`나 `Index`를 대신 쓴다.

## 4. 런타임 구조

### 4-1. 연출기 인터페이스

```csharp
public interface IFeatureEmitter
{
    void Emit(in FeatureNoteEvent e);     // 음 하나
    void Announce(in FeatureAnnounceEvent e);  // 루프 등장 1박 전 (선택 구현)
    void Tick(float dt);
    void Clear();
    int ActiveCount { get; }
}

public readonly struct FeatureNoteEvent
{
    public readonly FeatureLoopCatalog.Note Note;
    public readonly FeatureLoopData Loop;
    public readonly VoiceOverride Voice;
    public readonly float Pitch01;        // 스타일의 midiRange로 정규화된 높이
    public readonly int Side;             // SideMode로 결정된 -1 / +1
    public readonly float SecondsPerBeat; // 템포 구간에 맞춰 연출 길이 조정용
}

public sealed class FeatureVisualContext   // 연출기가 아는 세계의 전부
{
    public Camera Camera; public float ArenaRadius; public Material Material;
    public Sprite Dot; public Transform Root; public int SortingOrder;
}
```

### 4-2. 디렉터 `FeatureLoopVisuals`

지금 파일에서 박 추적 부분만 남기고 그리는 코드를 연출기로 뺀다.

```
Update
 ├─ SpawnFromMusic()            ← 기존 로직 유지 (프레이즈 경계, _lastPhraseBeat 비교)
 │    for note in Catalog.NotesById[loop.Id] (이번 프레임에 지난 것):
 │        style   = library.StyleFor(loopData, note.Instrument)
 │        emitter = GetOrCreateEmitter(style)      // 스타일 에셋당 하나, Dictionary 캐시
 │        if (budget 초과) skip or 약하게            // 5절
 │        emitter.Emit(new FeatureNoteEvent(...))
 ├─ Announce (프레이즈 마지막 박, UpcomingFeature가 있을 때)
 │        loopData.announce 스타일로 처리. 루프 안 각 악기 연출기에도 Announce 전달
 └─ foreach emitter: Tick(dt)
```

- `Side` 계산(지금의 `_cometSide`, `_birdSide`)은 디렉터가 악기별 카운터로 관리한다 → `SideMode`가 루프 데이터에서 바뀌어도 연출기는 몰라도 된다.
- `ResetVisuals()` → 모든 연출기 `Clear()`.

### 4-3. 기존 연출 이식

| 지금 코드 | 옮길 곳 |
|---|---|
| `Flyer` (혜성 부분), `Show`/`Animate`의 `!IsBird` 분기 | `CometEmitter` |
| `Flyer` (새 부분), `Wings` LineRenderer, 날갯짓 | `BirdEmitter` |
| `Announce()`의 반짝임 (`Sparkle`) | 디렉터의 `EdgeTwinkle` 공용 연출 (`SparkleEmitter`) |
| `CreateDot()` | `FeatureVisualContext.Dot` (디렉터가 한 번 만들고 공유) |
| 상수들 | `CometStyle.asset`, `BirdStyle.asset`의 기본값 |

1차 이식의 완료 기준은 **겉보기 차이 없음**이다. 같은 시드로 Brass Solo와 Whistle Hook을 띄웠을 때 혜성/새의 위치·색·타이밍이 지금과 같아야 한다.

## 5. 공통 규칙 (모든 연출기가 지키는 것)

- **레이어**: `SortingOrder = -3` 고정 (아레나 경계 -1, 공통 연출보다 아래, 적보다 아래).
- **중앙에서 퍼지는 원 금지**: 플레이어 펄스와 같은 모양이라 판정이 헷갈린다. 중앙 리플은 `MusicReactiveVisuals`의 피버 시작·끝 표시 전용이다.
- **아레나 침범 금지**: 연출기는 `ArenaRadius + 0.6` 안쪽에 머물지 않는다. 혜성처럼 화면을 가로지르는 것은 반투명(알파 0.75 이하)과 빠른 통과로 예외를 허용.
- **알파 상한**: 0.8. 적 색과 겹치지 않는 팔레트(따뜻한 노랑, 민트, 연보라 등)만 쓴다.
- **예산**: 라이브러리의 `maxActiveVisuals`를 넘으면 새 음표는 크기와 알파를 줄여서 내거나 건너뛴다. Latin Groove(16분 필인)나 Marimba Run처럼 음이 촘촘한 루프 대비.
- **템포 보정**: 연출 길이는 초 단위 기본값에 `SecondsPerBeat`를 곱해 쓰는 옵션을 둔다. 빠른 구간에서 연출이 겹쳐 쌓이지 않게.
- **예고**: 등장 1박 전에 `FeatureLoopData.announce` 스타일로 표시. 색은 `accent`.
- **공통 연출과의 관계**: `FeatureSounding` 동안 `MusicReactiveVisuals`의 세기를 낮추는 건 디렉터가 아니라 `MusicReactiveVisuals`가 `SoundManager.FeatureSounding`을 보고 처리한다 (서로 참조하지 않게).

## 6. 악기별 기본 스타일 (1차 안)

| 악기 | 스타일 | 화면 연출 | 음 높이 사용 | 비고 |
|---|---|---|---|---|
| Trumpet | `CometStyle` | 화면을 좌우로 가로지르는 혜성, 화음(3음)은 부채꼴로 여러 개 | 세로 위치 | 기존 |
| Whistle | `BirdStyle` | 아레나 옆 띠에서 날갯짓하며 올라가는 새 | 세로 위치 | 기존 |
| Mallets (마림바·실로폰·글록) | `ChimeStyle` | 아레나 바깥 띠에 작은 별이 톡 켜졌다 꺼짐, 음이 높을수록 위쪽·작게 | 세로 위치 + 크기 | 16분음표 대응 위해 짧게(0.35초) |
| Perc | `RimOrbitStyle` | 아레나 테두리 바깥을 도는 점, 타격마다 한 칸 전진·`Voices`만큼 밝게 | 사용 안 함 (`Voices`로 세기) | 7-4절 "라틴 퍼커션" 안 |
| Synth | `RippleStyle` | 아레나 경계 **바깥**에서 시작하는 원형 파동, 음 높이로 반지름 결정 | 반지름 | 7-4절 "신스 브라스" 안. 중앙에서 퍼지는 원은 플레이어 펄스와 헷갈리므로 금지 (중앙 리플은 피버 시작·끝 전용) |
| Guitar | `ShockStyle` | 화면 아래 가장자리에서 짧은 충격파 띠, 마지막 히트는 크게 | 사용 안 함 | 파워 코드 5번뿐이라 크게 써도 됨 |

### 루프별 덮어쓰기 후보

| 루프 | 덮어쓰기 | 이유 |
|---|---|---|
| 6 Call and Response | Trumpet `side = Left`, Whistle `side = Right` | 주고받기가 눈으로 보이게 |
| 5 Brass Solo | Whistle `sizeScale = 0.7` | 트럼펫이 주인공, 휘파람은 추임새 |
| 12 Mallet Hook | Perc `sizeScale = 0.5` | 뮤트 카우벨은 배경 박자 |
| 11 Power Chord Hits | `announce = RimPulse` | 다음 프레이즈로 밀어 넣는 느낌 |

## 7. 진행 순서

1. **카탈로그 통합** (오디오 쪽)
   `feature_loops.py`가 `FeatureLoopCatalog.g.cs`(enum, 루프 표, 음표)를 생성 → `FeatureSelector`의 손으로 쓴 표 삭제, `FeatureSelector.Instrument` → `FeatureInstrument`로 교체. 이 단계에서 7~12번 루프가 선택 대상에 들어오므로 FMOD 빌드에 실제로 들어가 있는지 같이 확인.
2. **구조만 바꾸기** (겉보기 변화 없음)
   `IFeatureEmitter`, `FeatureVisualStyle`, `CometEmitter`, `BirdEmitter`, `SparkleEmitter` 도입. 라이브러리 에셋 없이 `CreateDefault()`로 실행해서 기존과 같은지 확인.
3. **에셋화**
   `FeatureLoopLibrary.asset`, `CometStyle.asset`, `BirdStyle.asset`, 12개 `FeatureLoopData.asset` 생성. 선택 가중치·분위기 태그도 여기로 옮기고 `FeatureSelector`가 읽게 함.
4. **신규 스타일**
   `ChimeStyle` → `RimOrbitStyle` → `RippleStyle` → `ShockStyle` 순 (음이 많은 루프부터 덮어서 예산 규칙을 일찍 검증).
5. **루프별 덮어쓰기** 적용 후 플레이 테스트, 가독성 점검.

### 검증 방법

- **에디터 검사** (EditMode 테스트 또는 메뉴 명령): 카탈로그의 모든 id에 `FeatureLoopData`가 있는지, 루프에 쓰인 모든 악기에 스타일이 있는지 확인.
- **디버그 강제 재생**: 개발용 키로 다음 프레이즈의 특색 루프를 지정 → 루프 하나씩 눈으로 확인.
- **타이밍 확인**: 음표 수만큼 `Emit`이 호출되는지 카운트 로그 (예산으로 건너뛴 수 포함).

### 7-1. 1~3단계 구현 현황 (2026-11-24)

설계와 다르게 간단히 한 부분은 **(변경)**으로 표시했다.

- **1단계 카탈로그 통합**
  - `feature_loops.py`의 `write_cs()`가 `FeatureLoopNotes.g.cs`에 루프 표(`FeatureLoopNotes.Loops`)까지 생성한다. 악기 플래그는 음표에서 OR로 계산한다.
  - `FeatureSelector`의 손으로 쓴 표는 지우고 생성된 표를 쓴다.
  - 생성 결과 검증: 루프 표는 손으로 쓴 표와 같고, 음표는 `Whistle` 필드만 빠지고 동일하며, `feature_loops.js`(FMOD 쪽)는 바이트 단위로 같다.
  - **(변경)** 파일과 클래스 이름은 `FeatureLoopCatalog`로 바꾸지 않고 `FeatureLoopNotes`를 유지했다. 악기 enum도 `FeatureSelector.Instrument`를 그대로 쓴다 (이미 Python `FLAGS`와 값이 같다). 루프 id는 1..N 연속이어야 한다는 검사를 생성기에 넣었다.
  - `Note.Whistle`은 지우고 `Note.Instrument`로 판단한다.
- **2단계 구조 교체** — 코드: `Assets/Scripts/Visual/FeatureLoops/`
  - `IFeatureEmitter`, `FeatureVisualContext`, `FeatureVisualStyle`(색, 음역, 길이, 크기, `PitchToY`)
  - `CometStyle` + `CometEmitter`, `BirdStyle` + `BirdEmitter`: 예전 상수를 스타일 필드 기본값으로 옮겼고, 궤적과 페이드 계산은 예전과 같다.
  - `SparkleEmitter`: 예고 반짝임.
  - `FeatureLoopVisuals`는 디렉터만 맡는다: 박 추적, 음표 발사, 예고 타이밍, 스타일마다 연출기 하나를 만들어 캐시.
  - **(변경)** 좌우 교대(`SideMode`)는 아직 디렉터가 아니라 각 연출기가 직접 한다. 덮어쓰기가 필요한 루프(Call and Response)를 만들 때 옮긴다.
- **3단계 에셋화**
  - `FeatureLoopLibrary`(악기 → 스타일, 대체 스타일, 루프 데이터 목록), `FeatureLoopData`(루프 id, 예고 색, 악기별 스타일 덮어쓰기).
  - 게임은 `Resources/FeatureLoopLibrary`를 읽는다. 없으면 코드 기본값(트럼펫 = 혜성, 휘파람 = 새, 나머지 = 혜성)으로 돈다.
  - 에셋 생성: Unity 메뉴 **Chord Pulse > Create or Update Feature Loop Assets** → `Assets/Resources/FeatureLoopLibrary.asset`, `Assets/Resources/FeatureLoops/`에 스타일 2개와 루프 데이터 12개. 다시 실행하면 빠진 것만 추가한다.
  - **(변경)** 선택 튜닝(분위기 태그, 가중치, 숨 돌리기 허용)은 아직 `FeatureSelector`에 그대로 있다. 데이터로 옮기면 같은 시드의 선택 순서가 바뀔 수 있어서 따로 진행한다.
- **겉보기 차이**
  - 트럼펫·휘파람 루프(1~6): 없음. 궤적, 크기, 색, 좌우 교대가 예전과 같다.
  - 7~12번 루프: 음표는 예전처럼 혜성으로 나온다. 다만 예고 반짝임 색이 민트(새 색)에서 금색(혜성 색)으로 바뀌었다. 예고 색이 리드 악기 스타일의 색을 따라가는데, 아직 전용 스타일이 없어서 혜성으로 대체되기 때문이다. 4단계에서 악기별 스타일이 생기면 맞춰진다.
- **확인**: 독립 컴파일과 Unity 에디터 컴파일 모두 성공. 플레이 확인 완료 (겉보기 차이 없음).

### 7-2. 4단계 신규 스타일 (2026-11-24, 플레이 확인 전)

- `ChimeStyle`(말렛), `RimOrbitStyle`(퍼커션), `EdgeRippleStyle`(신스), `ShockStyle`(기타), 그리고 피버용 무지개 `CometStyle`. 자세한 모양은 [MusicVisualsPlan.md 5-1](MusicVisualsPlan.md).
- `IFeatureEmitter.Emit(note, sizeScale, side)`: 루프별 크기와 좌우 고정을 연출기에 넘긴다. `SideMode`는 `FeatureSide`(Auto/Left/Right)로 단순화했다.
- 이제 7~12번 루프의 예고 반짝임도 각 악기 색이다.
- 에셋 메뉴는 코드 기본값(`CreateDefault`)을 그대로 저장한다. 이미 에셋이 있으면 빠진 악기 스타일, 피버 스타일, 루프 데이터, 비어 있는 덮어쓰기만 채우고 손댄 값은 그대로 둔다.

## 8. 피버와 특색 루프 (2026-11-24 갱신)

### 8-1. 피버 규칙 (변경 후)

- 8번째 처치에 `QueueFever()` → "FEVER READY"로 대기한다.
- 피버는 **프레이즈 하나 전체(4마디)**를 채운다. 빌드업은 **그 앞 프레이즈의 4마디째**다.
- 아래 두 경우에는 피버를 한 프레이즈 더 미룬다.
  - 빌드업 마디가 이미 너무 가깝다 (FMOD 앞보기 0.15초 안쪽).
  - 현재 특색 루프가 4마디째에 연주된다 (스네어 롤과 겹치므로).
- 다음 프레이즈에 미리 뽑아 둔 루프는 항상 취소한다 (`FeatureSelector.CancelNext()`). 피버가 끝날 때까지 새 루프를 뽑지 않는다.
- 피버 프레이즈가 시작되면 피버 다음 프레이즈의 루프를 정상적으로 뽑는다. 그래서 피버 마지막 박에 예고 반짝임이 나오고, 피버가 끝나자마자 손님이 들어온다.

### 8-2. 예전 문제가 어떻게 됐는지

| # | 예전 증상 | 새 규칙에서 |
|---|---|---|
| A | 4마디 루프 중간에 피버가 걸려 소리와 연출이 끊김 | **해소.** 빌드업 마디에 루프 음이 있으면 피버를 미루기 때문에, 빌드업이 시작될 때 이미 루프 음이 끝나 있다. 그래서 따로 퇴장 연출을 넣지 않는다 (한때 넣었던 `Farewell()`은 실행될 일이 없어 되돌렸다). |
| A' | 빌드업 직전 마지막 8분음표가 0.15초 앞보기 때문에 잘림 | **해소.** 4마디째를 쓰지 않는 루프는 늦어도 3마디째 안에 끝나므로, 앞보기 구간에 걸리는 음이 없다. |
| B | 피버가 끝난 뒤 예고 없이 루프 후반부만 튀어나옴 | **해소.** 피버가 프레이즈 경계에서 끝나고, 다음 프레이즈 루프는 미리 취소된다. |
| D | 취소된 루프도 "최근 등장"으로 기록됨 | **해소.** `CancelNext()`가 기록에서도 뺀다. |
| C | 피버 4마디 동안 화면이 비어 보임 | **남음.** 아래 8-3. |
| E | `visualLatencyMs`를 켜면 프레이즈 끝 음이 안 그려질 수 있음 | **남음** (지금은 값이 0이라 문제 없음). 지연 보정을 켤 때 처리. |

### 8-3. 남은 일

1. **C: 피버 프레이즈 연출.** 피버가 정확히 프레이즈 하나가 됐으니, 특색 루프와 같은 방식으로 다룰 수 있다.
   - (a) 권장: `FeatureLoopLibrary.feverStyle` 하나를 두고, 피버 프레이즈 동안 킥·스네어 박에 맞춰 그 연출기를 돌린다.
   - (b) 피버 전용 특색 루프 (`FeatureMood.Fever`): 소리까지 추가해야 해서 작업량이 크다.
2. **미루기로 생기는 빈 프레이즈.** 피버가 한 프레이즈 미뤄지면 그사이 프레이즈의 루프도 취소된다. 1~3마디만 쓰는 루프는 살릴 수 있지만, 그러려면 `UpcomingFeature`의 예고 조건도 같이 바꿔야 한다 (지금은 빌드업 마디가 있는 프레이즈를 "피버와 겹침"으로 보고 예고를 막는다). 플레이해 보고 허전하면 그때 손본다.
3. **E: 프레이즈 기준 통일.** 디렉터가 프레이즈 시작을 화면 박 기준으로 계산하도록 바꾼다. 지연 보정을 켤 때 같이 한다.

### 8-4. 확인 방법

- 루프별로 피버를 거는 시나리오: 4마디째를 쓰는 루프(Trumpet Rise, Brass Solo, Latin Groove 등) 중에 피버를 걸면 한 프레이즈 미뤄지는지, 쓰지 않는 루프(Trumpet Fanfare, Whistle Hook 등) 중이면 바로 다음 프레이즈에 피버가 오는지 확인.
- 피버 앞뒤 3프레이즈 동안 `FeatureLoop` 파라미터 값, `CurrentFeature`, `UpcomingFeature`를 로그로 찍어서, 루프가 피버와 겹치지 않고 피버 직후 예고와 함께 들어오는지 확인.

## 9. 열린 질문

- 스타일 에셋 대신 **프리팹 기반 연출**도 허용할지? 지금은 전부 코드로 그리지만, 나중에 손으로 만든 스프라이트 애니메이션(종이비행기 등)을 쓰고 싶으면 `PrefabStyle : FeatureVisualStyle`을 하나 추가하는 것으로 대응 가능.
- 7-5절 보너스 오브젝트(혜성을 맞히면 피버 게이지 +1)를 넣으면 연출기가 충돌체를 가져야 한다 → 그때는 `IFeatureEmitter`와 별도로 게임플레이 스포너가 같은 `FeatureNoteEvent`를 받게 하는 편이 낫다 (연출과 판정 분리).
- 피버 전용 특색 루프가 생기면 `FeatureMood.Fever` 루프는 피버 연출(`MusicReactiveVisuals`) 위에서 어떻게 보일지 따로 정해야 함.
